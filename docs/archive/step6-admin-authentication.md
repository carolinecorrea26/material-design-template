# Step 6 — password and authenticator setup

The October 5 scope implements the authentication portion of Step 6 first and
stops before Steps 4 and 5. Caroline's local admin account uses a password plus
a time-based authenticator code. Regular sign-in displays password and authenticator prompts; enrollment details appear only during setup.

## User flow

1. Run `npm run dev` and open `http://127.0.0.1:5180/admin-center`.
2. For a new account, choose a password of 12–256 characters. The username is
   `caroline`; the synthetic email remains `caroline@example.invalid`.
3. Add a time-based account in an authenticator app by scanning the displayed QR
   code. If scanning is unavailable, enter the displayed manual setup key.
4. Save the eight one-use recovery codes offline, then enter the current six-digit
   authenticator code to finish setup.
5. On later visits, enter the password followed by the authenticator code. The QR
   code and setup key appear only when enrolling an authenticator.

QR images are generated by the local API from the enrollment URI. No external QR
service receives the setup secret. Status responses contain no setup credentials.
Secrets and codes are removed from the rendered UI after successful verification
or sign-out. The server retains its existing owner-only local state file,
password/recovery hashes and expiring HttpOnly/SameSite session cookies.

Unfinished enrollment can resume after a reload or server restart: sign in with
the password, choose **Set up authenticator**, and scan the new QR code. This
replaces the unfinished secret and recovery codes. A verified account cannot
replace its authenticator using the password alone.

A saved recovery code is accepted only after password sign-in. Recovery revokes
other sessions and requires replacement enrollment and verification. The old
TOTP cannot complete a recovery session before replacement enrollment. Replacement
setup also invalidates other sessions and replaces the recovery-code set.

## Login lifecycle cleanup

- **Forgot password?** verifies a fresh authenticator code or one-use recovery
  code, replaces the password, revokes all sessions and returns to sign-in. There
  is no simulated email reset link. Recovery-code resets require a replacement
  authenticator, including after a server restart.
- **Change password** requires the current password and an already verified
  authenticator session. It revokes all sessions and requires fresh sign-in.
- Passwords expire exactly 30 days after setup, reset or change. Expired passwords
  allow password/MFA verification and password change; server-side admin APIs
  reject access until the password is changed. Reusing the current password is
  rejected. Forms confirm new passwords before submission.
- Existing accounts preserve their password, authenticator and saved work. Their
  first expiry window starts when the upgraded server loads the account, and the
  timestamp persists across restarts.
- Session status refreshes every 30 seconds and on window focus, returning expired
  sessions to sign-in. Authenticator enrollment secrets are not shown on normal
  sign-in. The authenticated toolbar offers password change and sign-out.

## Passkeys, account settings, and groups — October 5 update

Password entry now leads to a choice of registered passkey or authenticator
code. First-time enrollment can use a device passkey without an authenticator
app. Existing verified accounts must verify their current method before adding
a passkey in **Account settings**, reached through the account icon. The header
no longer includes the persona selector, signed-in identity, password-change
button, or sign-out button; those controls live in account settings.

Passkeys use native browser WebAuthn and local Node crypto verification. The
mock server supports ES256/P-256 credentials with none attestation, requires
user presence and verification, validates the exact browser origin and RP ID,
and binds a five-minute single-use challenge to the password-authenticated
session. Credential keys and counters persist in the existing private server
state. Registration requests target device authenticators; the device can use
biometrics or its screen-lock PIN. Biometric data never reaches the server.
This verifier is scoped to the localhost mock preview, not a production
identity deployment. The requested SimpleWebAuthn dependencies were blocked by
the package registry; no new dependency was installed.

Passkey-only setup provides eight recovery codes and requires acknowledgment
before opening administration. Recovery codes revoke that account's other
sessions and old passkeys, and require replacement enrollment. At least one
usable method must remain when removing a passkey. Password changes and resets
revoke only the affected account's sessions. Forgotten-password reset currently
uses authenticator or recovery-code proof, so passkey-only users should retain
recovery codes.

**Accounts & groups** includes Portal Team, Account Managers, Majesco, and TPA.
Caroline belongs to Portal Team and is the sole editor. Each group has a reviewer
account awaiting setup; Caroline can assign its initial password or add individual
accounts. No shared default passwords are provided. Each person signs in with
their own username/password and enrolls their own passkey or authenticator.
Group-specific views and scopes remain deferred; every group sees the same
workspaces, including the directory, while all operational edits and account
provisioning are restricted to Caroline by the server. Self-service password
and passkey management remains available to every signed-in account.

Operational records (Sites, Changes, Releases, Applications, audit history, and
migration schedules) now persist on the mock server instead of relying on
browser-only edits. Caroline's existing local operational records are imported
once if present, preserving prior work without overwriting subsequent shared
server changes. Canonical Library/applicant data retains its existing boundary.
The mock seed export also produces operations-data.json for startup.

User stories:

- As Caroline in Portal Team, I can edit operational data, manage accounts, and
  register a passkey from account settings after verifying my existing method.
- As a Portal Team reviewer, I can inspect all workspaces without saving changes.
- As an Account Manager, I can review client sites, requests, and releases with

- As a TPA reviewer, I can inspect sites, applications, and reporting without

- As any account holder without an authenticator app, I can enroll a device

## Local passkey domain and Master Admin management — October 6 update

The local Admin Center now redirects IP-based URLs to
`http://localhost:5180/admin-center`. Numeric loopback addresses can be secure
contexts while still failing WebAuthn relying-party domain validation. Passkey
options and verification use the `localhost` RP ID and exact localhost origin;
the server rejects IP-origin ceremonies. Moving between hostnames requires a
fresh sign-in because their authentication cookies are separate. The browser
helper also prevents IP-based requests and provides an actionable error when
an embedded browser cannot use the passkey domain.

Account settings no longer shows a passkey-name input at rest. **Add a device
passkey** opens a dialog with an optional name. **Create passkey** then starts
the device ceremony; cancellation leaves the account unchanged.

Caroline now belongs to both **Portal Team** and **Portal Master Admin**. Existing
account state is migrated on server startup without replacing credentials or
saved operational records. Portal Master Admin membership determines account
management authorization, independently of the existing Caroline-only portal
editing permission. Other Master Admins can manage accounts but retain read-only
portal access.

The **Account management** section supports account creation/setup, profile
updates, primary portal-group assignments, Master Admin membership, suspension,
and re-enablement. Master Admins can reach it from the sidebar or their account
settings. Other groups can view the directory without management controls.
The server checks membership for every account mutation, prevents suspension of
the current account, keeps at least one active Master Admin, and immediately
revokes sessions belonging to suspended accounts. Suspended accounts cannot
sign in or reset their password to bypass suspension.
