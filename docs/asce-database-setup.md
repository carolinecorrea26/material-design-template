# ASCE local database setup and verification

October 13, 2026. Scope: local ASCE prototype, with the shared schema supporting the other existing Sites. The fresh and upgrade gate applies the entire ordered migration directory, generates the current reviewed seed, and exercises real PostgreSQL relationships. It never reads Supabase credentials or resets a configured portal database.

## Storage boundaries

| Store | Purpose | Current access |
| --- | --- | --- |
| Reviewed Library exports | Site configuration, products, rules, fields and relationships | Generated by `npm run mock:seed`; served by the local mock platform |
| `.mock-platform/server-state.json` | Saved Library drafts, mock releases, operational edits, synthetic payments and receipts | Local server; atomic file writes; saved drafts take precedence for their Site |
| `.mock-platform/server-state.json.applicants.json` | Applicant save/resume values and expiring recovery capabilities | Separate local mock applicant service |
| Browser persistence adapter | Offline business records and fallback collections | Local storage; mock adapter now sends reads and writes to the same backing store for each table |
| Disposable PostgreSQL databases | Complete SQL schema, constraints, upgrade and ASCE application checks | Existing `portal-migration-review` Docker container; each review database is removed after checking |

The browser prototype uses its existing mock stores. PostgreSQL verification does **not** switch that runtime to SQL, and applicant save/resume and mock submission receipts do **not** become normalized operational application rows. A SQL-backed application service and deployment remain separate work. The browser fallback does not implement every SQL constraint. This distinction must be preserved when reporting readiness.

## Verified SQL structure

The chain contains 23 migrations and creates 147 public tables. The full schema gate checks fresh installation and upgrade from the earlier application-relationship schema. Upgrade fixtures retain an existing historical application with its original product label and explicit import evidence. Reapplying the current seed leaves the checked Site, Association, product, field and configuration snapshot unchanged.

The business hierarchy is TPA → Association → Site. Canonical Association identities retain legacy aliases and source records; `clients` remains a compatibility storage name for hosting Associations. ASCE gets one automatic Association context without a membership-choice selector.

Application people retain hosting Association tenancy. Composite relationships keep the application, Site, person and applicant role consistent. Coverage selections reference assigned, enabled Site products; riders reference their exact product assignment and Association/Site scope. Answers reference known fields and people within the same application.

The October 13 migration closes coverage/person role mismatches, disabled coverage selection, reparenting submitted answers or selections, clearing a submission timestamp, changing submitted identity, and changes to submitted people, participants or Association context. Submission requires a current captured snapshot. Editing answers after capture requires a new snapshot; both versions remain immutable.

Historical coverage-role mismatches, if present in a different database, are retained in the reconciliation ledger and leave the corresponding constraint unvalidated. The completion gate fails when any constraint remains unvalidated; it does not silently invent replacement records.

## Repeatable verification

With the existing local `portal-migration-review` PostgreSQL container running:

```sh
npm run db:verify-schema
npm run db:verify-asce
npm test
npm run build
npm run lint
```

`db:verify-schema` always exports a fresh reviewed seed, applies every migration in filename order, checks seed stability, validates ASCE application storage and anonymous data isolation, and records fresh/upgrade evidence in [postgres.json](schema-validation/postgres.json). The installed column and constraint inventory is captured directly from PostgreSQL in [table-dictionary.json](schema-validation/table-dictionary.json), rather than inferred from a partial migration manifest.

`db:verify-asce` also runs the ASCE MCR/approved-decision, coverage runtime, applicant save/resume and prototype restart tests. These are synthetic prototype checks; real PRASE, real payments and hosted authentication are outside this scope.

The local browser check confirms the ASCE Library loads, Membership validates required inputs, saves a synthetic applicant, advances to Eligibility and retains Membership values after reload. The development preview is available at `http://127.0.0.1:5180/?site=asce`.

The earlier [step 1 audit](schema-step1/audit.md) is historical evidence. Its 135-table count and open implementation states describe the pre-upgrade schema, not the current installed validation result. ASCE source completeness and remaining rich-preview/configuration parity work in the [Library model review](portal-library-model-review.md) are separate from successful SQL structure checks.
