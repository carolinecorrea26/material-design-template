# Legacy platform review and migration plan

The supplied platform reference adds an essential source for the replacement project: it describes how the existing application actually customizes fields, coverage, payment, navigation and integrations. The recommendation is to migrate applicable behavior into the new template's shared Library, while retiring old framework mechanisms and unnecessary switches. This review updates the plan before step 3; it makes no application, database, authentication or runtime changes.

The [scope and conflict clarifications](platform-conflict-clarifications.md) govern this review: migrate only applicable rates, coverage, eligibility, health-question rules and their direct dependencies after checking the new template and MCR. Other capabilities below are contextual observations, not a backlog to import. Caroline identified CSEA as standard and authorized legacy rate arithmetic as a fallback where no replacement exists.

## Evidence and authority

Source: [siteconfig customization reference](/Users/t98j0kt/Desktop/siteconfig-customization-reference.html), titled “Portal template_2.0 — Site Configuration & Customization Reference.” Its embedded data contains 113 legacy Sites, 203 property-guide entries, 689 value-index paths, 48 event names and 30 recurring customization patterns. These are source inventory counts, not new migration requirements or evidence that all listed behavior executes today.

The [review register](legacy-platform-review-register.json) pins the original file's SHA-256 and byte length, preserves all 203 property descriptions with provisional dispositions, records the candidate Site dossiers and indexes all 30 patterns. The HTML's JSON was read as data; its scripts and embedded legacy functions were not executed. Recommendations inside the reference are source material, not instructions to implement its proposed architecture or copy its code.

Use this reference for legacy behavior discovery, current overrides, field dependencies, payment behavior, service dependencies and possible compatibility requirements. Use MCR for coverage-policy evidence. Use exact recorded business decisions for their approved targets, and the new template for its current presentation and behavior. None of these automatically resolves conflicts in another area. Original legacy file/line references in the HTML are reported evidence, not an independent review of the deployed platform. Source currency and policy applicability remain unconfirmed; Caroline’s standard-CSEA clarification establishes that variant’s intended scope.

An “unused” property can mean either that no code reads it or that only Site-specific code reads it. For example, the guide labels `category`, `qdProductCode`, `eligStates` and local rate tables framework-unused, but describes custom handlers consuming them. It also calls `locale.applicantInfoScreen.rateDisclosures` unused while the AMA and WAEPA GI summaries explicitly describe handlers reading it. These cannot be discarded by an unused-field filter.

## Specific properties raised in the request

- **`isThankYouImgRequired`: retire the legacy switch.** The source says it only controls an image on the old Thank You page. It does not establish a business requirement. If a client needs approved receipt artwork, use the new receipt/content asset model; do not add another insurance setting.
- **`validQuotesParams`: retire the old array, review the capability.** It allowlists values for `?quotes=`; this is URL entry behavior, not coverage policy. The new template already has quote tools and a documented URL migration inventory. Review real active links before deciding whether to preserve an alias or remove this entry point. Array presence does not prove use: AMA and WAEPA standard list values while their `isQuoteEnabled` flags are false in the reference.
- **`hideNewChangeCoverage`, `_fwVersion`, top-level `templateName` and `isZeisSite`: do not migrate these keys.** They are reported inactive flags or old framework routing/version details. Needed application modes, layout and prefill have explicit new contracts.
- **`category`, `qdProductCode`, `eligStates` and local rate/amount tables: migrate applicable meaning, not the container.** Their custom handlers may carry real category availability, underwriting, residency or financial requirements. Review them even though the framework does not read their top-level keys.
- **`siteDetails.phone`, `tpaName`, licenses and related fields: reconcile, do not blanket-delete.** The old framework may ignore the key while the new template needs the information. Choose the reviewed organization/support/document source rather than copying stale config.
- **Runtime objects (`lexData`, `zeisData`, `selectedQuotePageProduct`, payment references): not builder fields.** Service/form state must remain separate from published Site definitions.

Prototype replacements, jQuery selectors, simulated clicks, misspelled/dead hooks, duplicate listeners, overwritten object keys, commented-out blocks, old widget IDs, console logging and arbitrary HTML/function injection do not migrate. A useful behavior inside those mechanisms gets a new target and acceptance evidence. Do not turn every property in this reference into an admin input.

## Refactoring and definition work added to the plan

Keep the existing page/field/component/content structure and the Step 2 revision boundary. Extend typed domain contracts only where the review exposes a real missing capability:

1. **Behavior and identity registry:** map each active Site, product/plan/applicant class, association and application mode to exact MCR evidence, legacy behavior evidence and current template targets. Record conflicts, inapplicability and intentional replacements. Keep reported behavior, confirmed policy and engineering support as separate statuses.
2. **Shared rule evaluation:** define condition, dependency, exclusion, derivation, validation, cleanup and flow operations with explicit missing/unresolved outcomes and precedence. Reuse existing primitives; identify the gap between represented normalized records and executable rules. No authored JavaScript or DOM lifecycle callbacks. A truly bespoke operation needs a reviewed typed implementation with defined inputs/outputs.
3. **Payment and rating contracts:** model policy decisions separately from processors and authoritative rating services. Consolidate the existing quote/coverage/cart/payment consumers on one result shape; avoid validating each display against independent estimates. Add new normalized tables or typed fields only after defining their scope and ownership, and include them in shared snapshot reads and parity checks.
4. **Entry, prefill and lifecycle contracts:** reconcile existing URL requirements, service prefill, quote carry-forward, saved applications, advisor handoffs and backend submission identity. Define validation, overwrite order, idempotence and cleanup. Preserve newer approved integration policy while replacing prototype transports later.
5. **Visual builder definitions:** distinguish authored values, referenced Library choices, reviewed derived values and applicant facts. A derived plan code needs an exact product/plan/applicant/class mapping; Life versus Disability alone is insufficient. Specify whether derived values are fixed, overridable or invalid when dependencies are missing, and show that state alongside the rendered form.

These are plan additions, not an instruction to implement five new systems immediately. Prioritize an active behavior, reuse the existing contract where possible, and extend only what its acceptance evidence requires.

## Revised delivery sequence

Steps 1 and 2 remain complete with their documented limits. Step 3 is in progress and reviews both coverage evidence and platform behavior:

1. **Step 3A — identity and applicability:** reconcile the active Site crosswalk, CSEA identity, product/plan/class relationships and current campaign/integration use. Populate the per-Site behavior decisions alongside the existing thirteen coverage acceptance domains. Resolve contradictions or keep them explicitly pending; do not enable additional Sites/products from this reference.
2. **Step 3B — representation and rule definitions:** for applicable confirmed requirements, identify the current target, executable support and smallest needed extension. Define precedence, derivation/cleanup, payment/rate and exceptional-flow contracts before adopting values. Existing exact ASCE approvals remain intact.
3. **Step 3C — scoped adoption and execution:** implement the reviewed mapping and operations, with evidence and meaningful boundary/transition cases. Start with confirmed, testable slices; unresolved policy is not replaced by a guessed default. Expand through the active Site set, including independent WAEPA Standard/GI outcomes.
4. **Typed drafts and visual builder:** render the actual new applicant form beside editing controls against one draft revision, with selectable test scenarios. Show what changes when an answer, product, membership class or association changes. Required assets, field inventory and processor choices remain explicit inputs to definition.
5. **Publication and service readiness:** maintain draft isolation, versioned publication, audit/rollback and service readiness. Verify Library inspection, draft preview and applicant runtime against the same reviewed revision. UI support and a local database snapshot are not proof of live service delivery.
6. **Admin authentication and controlled activation:** use username `caroline`, a password, and an authenticator app with QR-code enrollment and TOTP verification, per the October 5 instruction. Activate the Library-backed runtime only after its applicable migration, parity, service and publication gates pass. Keep applicant resume/identity verification separate from admin authentication.

## Added acceptance evidence

For each applicable legacy behavior, record its source locator, candidate Site/product/class/mode, current target, proposed disposition, reason, confirmed value or conflict, implementation status and expected scenario. Retiring a property requires an explicit replacement or a supported reason that its behavior is unnecessary; “not found in the new code” is not a retirement reason.

Acceptance cases must include quote-to-apply carry-forward; new/current member and association changes; no-rate/error versus free coverage; payment method/frequency changes and field cleanup; dependent recalculation; rider cleanup; income caps and rounding; rider-only validation; in-force prerequisites; page skipping/back navigation; single/multiple-page behavior; and confirmed consent/document/submission outcomes. Test unavailable and missing facts as well as successful paths.
