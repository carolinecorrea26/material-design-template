## Review organization

MCR-specific or explicitly unique behavior must be represented by reusable **global definitions/typed configuration**, with explicit assignments and values for the Sites that require it. A source describing only one Site is evidence for its assignment, not a reason to add a Site-name branch or make its values global defaults. Retain existing structured policies, fields, conditions and dedicated resolvers; record unsupported contracts/predicates as gaps before activation. This authoring requirement applies to the full crosswalk, including source-only and planned behavior.

Use one coverage register with the following areas. A requirement may link to several areas, with one primary execution owner. Review underlying behavior even if the new template moved its fields to another page.

| Area | Requirements to reconcile |
| --- | --- |
| Membership | Association qualifications, nonmember participation, verification and active-duty restrictions |
| Eligibility | Applicant roles, spouse/child participation, age, residence and dependent facts |
| Coverage | Category questions, eligibility, availability, amounts, dependencies, aggregates, rider conditions and changes to selected products |
| Health | Underwriting pathway selection, page participation, question applicability and follow-ups |
| Beneficiary | Applicable coverages, collection, relationships, shares and validation |
| Profile | Insurance history, repeatable records, follow-ups and advisor handoff |
| Contact | Address/phone requirements, carry-forward and conditional collection |
| Review and consent | Applicable consent blocks, acknowledgements, jurisdiction fraud notices and required signatures/dates |
| Payment and rates | Payment methods/frequencies, premiums, modifiers, fees, suppression and submission gates |
| Navigation and validation | Page participation, ordering, conditional skipping, single/multipage behavior and advancement validation |
| Save and resume | Retention, expiry, attempts, revocation, single use, recovery isolation and changed-revision revalidation |

## Execution plan

1. **Build the requirement crosswalk.** Enumerate atomic requirements from in-scope MCR cells and current template behavior. Split cells containing multiple instructions. Link all catalog records back to requirements or an explicit template rationale, including planned and source-only records. Each row records source/decision, area, Site/product/applicant/mode scope, expected behavior, rule ID, actual stored policy or service owner, implementation consumer, verification evidence and disposition. The initial named gaps below are a starting batch; the full requirement enumeration remains open.
2. **Reconcile execution ownership.** For each row, identify the existing field, condition, product policy, scoped assignment, routing rule or service contract that owns execution. Retain structured policies and dedicated resolvers. Rule descriptions must reference them. Resolve duplicate values at the owner and derive compatibility views. Validate unsupported predicates, ambiguous assignments and contradictory overrides before activating a revision. Apply this to every area above, beginning with Membership, Eligibility and Coverage, then Health through Payment, then cross-application behavior.
3. **Make the Library the review and editing entry point.** Extend Rules browsing with coverage status, source evidence, execution owner and verification status alongside area and applicability. Add direct navigation to the actual owning fields/conditions/policies and show inherited versus scoped values. Keep documentation-only, executable, planned and source-reference status distinct from coverage status. A prose edit must not silently alter behavior. Service-owned controls must clearly identify their service and current mock scope; adding their catalog records does not make their constants Library-editable.
4. **Complete each gap and propagate it through the existing revision pipeline.** Save authored definitions and scoped policies in the Library snapshot. Compile and validate the reviewed seed, then resolve the captured Site revision into runtime fields, questions, products and decisions. Quote, category alerts, product selection, page advancement and downstream validation must use those same decisions. Verify a stored policy edit changes the intended Site and leaves unrelated Sites unchanged. New prototype sessions load regenerated reviewed data after the mock server reloads it. Existing saved drafts/releases require an explicit compatible migration or a newly based draft and release; preserve application and historical snapshots. This work does not redesign Site Builder.
5. **Close areas with evidence.** For each applicable requirement, record boundary/missing/invalid-answer checks and a rendered journey case when presentation matters. Verify persistence, reload and scoped isolation. A completed area has no undispositioned requirement, no competing execution owner and no unexplained catalog behavior. Accepted provisional and explicitly deferred work retain visible dispositions. The whole rules review closes only when every area meets this gate; a larger rule count or a successful build is insufficient.
